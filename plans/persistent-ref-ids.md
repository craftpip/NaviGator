# Persistent Incremental Reference IDs

## Goal

Make every `ref_id` permanent across Navigator restarts. A URL keeps the same
reference ID forever, new URLs receive the next unused integer, and old IDs
continue to resolve through `web_fetch`, `web_page_links`, and devtools after a
restart.

## Current Behavior

`src/ref-memory.js` owns both the allocator and resolver:

- `nextLinkRef` starts at `1` whenever Node starts.
- `linkMemoryByRef` and `linkMemoryByUrl` contain at most 2,000 entries.
- Pruning removes the only URL-to-ID mapping, so an older ID cannot resolve
  even before a restart.
- `src/mcp-server.js` calls `rememberLink()` for search result URLs, fetched
  pages, page links, and screenshots. `src/devtools.js` resolves IDs through
  the same module.

The SQLite database is initialized before serving MCP requests and persists at
`data/navigator.db`, but it currently has no reference-link table.

## Design

Add a durable `ref_links` table and make it the source of truth:

```sql
CREATE TABLE ref_links (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  url TEXT NOT NULL UNIQUE,
  created_at INTEGER NOT NULL
);
```

- `AUTOINCREMENT` ensures SQLite never reuses a previously committed ID, even
  if rows are later removed manually. The application will not prune this
  table.
- `url` uniqueness preserves the existing exact-string URL behavior. Do not
  introduce URL normalization as part of this change, because it could merge
  references that currently receive distinct IDs.
- The existing maps remain a 2,000-entry read-through cache only. Eviction
  must never delete a database row.
- Database lookup makes an old ref resolvable after a restart or cache eviction.
- The table intentionally has no foreign key to activity tables and is excluded
  from the seven-day activity-pruning job.

## Implementation Steps

1. Add the `ref_links` migration to `MIGRATIONS` in `src/db.js`, with a unique
   URL constraint and an index only if query-plan inspection shows the unique
   index is insufficient. This becomes the next schema version automatically.
2. Add small database helpers in `src/db.js`:
   - `rememberRefLink(url)` inserts a previously unseen URL and returns its ID.
   - It must use an insert-or-ignore/upsert followed by a select, so repeated
     calls always return the original ID and a uniqueness conflict cannot create
     a second ID.
   - `getRefLinkById(id)` returns the URL or `null`.
   - `getRefLinkByUrl(url)` returns the ID or `null`.
   - Keep database statements scoped to initialized database access; do not add
     a second connection or a new data-directory setting.
3. Refactor `src/ref-memory.js` to delegate canonical reads and writes to those
   helpers:
   - `rememberLink(url)` validates and trims as it does today, checks the URL
     cache, then persists/reads the ID and populates both caches.
   - `getUrlForRefId()` and `getLinkRefByUrl()` check cache first, then query
     SQLite and warm both cache maps with the returned record.
   - `resolveRefIdToUrl()` keeps its existing error contract when no row exists.
   - Keep cache pruning, but limit it to the maps. A cache miss is no longer a
     lost reference.
   - Remove `nextLinkRef` and the legacy string-or-object compatibility branch;
     all records are now generated by one durable path.
4. Verify startup ordering in `src/mcp-server.js`: `initDb()` must still run
   before any call that can invoke `rememberLink()`. Ensure no test or CLI path
   imports/refers to `ref-memory.js` before initializing a temporary database.
5. Add focused tests, preferably `tests/ref-memory.test.js`, using a temporary
   data directory and `closeDb()` isolation:
   - first URL receives an ID and repeating it receives the same ID;
   - a second distinct URL receives a larger ID;
   - close and reinitialize the same database, then verify both forward lookup
     and reverse lookup still work;
   - verify the next newly inserted URL after reinitialization is greater than
     every existing ID;
   - insert more than the cache limit (or expose/reset cache state only for the
     test) and verify an evicted ID still resolves from SQLite;
   - unknown IDs preserve the current `null`/throw behavior.
6. Add or extend an MCP-level test that performs a search/fetch, restarts only
   the database/ref-memory test fixture, then calls `web_page_links` or a
   `ref_id` fetch to prove the public resolution path is durable. Do not make a
   live browser request for this test; reuse the existing mocked server setup.

## Migration and Operations

- Existing in-memory IDs cannot be recovered after the server has restarted;
  there is no historic mapping to migrate. The first deployment begins storing
  every newly seen URL permanently.
- The table grows with unique URL strings and has no retention policy. This is
  required for permanent resolution; database backups should include
  `data/navigator.db`.
- If an operator intentionally deletes rows, their IDs remain unassigned and
  will not be reused because of `AUTOINCREMENT`.
- No MCP schema or client-call changes are needed. `ref_id` remains a positive
  integer, but it is no longer expected to be small or reset per process.

## Verification

1. Run `docker compose exec navigator npm install --include=dev`.
2. Run `docker compose exec navigator npx vitest run tests/ref-memory.test.js tests/mcp-server.test.js`.
3. Run `docker compose exec navigator npm run lint`.
4. Restart the container, search or fetch a known URL, and resolve its prior
   ID through `web_page_links` and `web_fetch(ref_id: ...)`.
5. Inspect `data/navigator.db` to confirm `ref_links` rows survive the restart
   and the subsequent ID is greater than the previous maximum.
